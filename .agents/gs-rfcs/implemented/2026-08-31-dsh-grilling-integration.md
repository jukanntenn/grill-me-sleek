# GS-RFC: DeepSeek Harness integration — `grill_user` as a first-class Hub client

Status: implemented

English | [中文](2026-08-31-dsh-grilling-integration.zh.md)

## Problem

grill-me-sleek today reaches AI agents through one shape only: a subprocess CLI (`@grilling-sleek/cli`) that the agent shell outs to — create session, poll rounds, push answers — over the public Hub, with the web SPA as the answer surface. That shape was designed for agent tools whose only extension point is "run a command". DeepSeek Harness (dsh) is the opposite kind of host: an all-plugin Cordis harness where tools, session-event logging, approvals, and the agent loop are all plugins, and a subprocess CLI is six mismatches deep — validation sits on the wrong side of a process boundary, cancellation (`exec.signal`) cannot reach `poll --wait 600`, the CLI's 600 s budget fights the tool timeout model, round state lands in the Hub DB with only a weak link to the host's own session log, approval semantics overlap, and `npm install -g` plus Hub reachability become deployment variables. A completed design session (v2, source-reviewed against a reference clone of the Harness) settled the target shape; this record carries its decisions and gates the implementation, which lives in this repository under `dsh/`. The Hub itself is in scope only to stay compatible.

## Decision

dsh is a first-class Hub API client, exactly like the agent tools the CLI serves. One npm package in this repository — `dsh/`, published as `@grilling-sleek/dsh-tool-grill-user` — registers the tool `grill_user`; the Hub changed nothing. Five decisions define the shape:

1. **Question core goes native.** `grill_user` maps a grilling question batch (the `schemas/grilling.json` vocabulary, internalized as the tool parameter schema) onto dsh's `ctx.userQuestions.ask()` — so every answerer already in the waterfall (official desktop card, IM bridges, remote apps) works with zero code, first answer wins across them by gateway arrival order. Question ids carry a forced `grill_` prefix. The skill survives as a runtime-registered skill (`ctx.skills.register`): same triggers (`/grilling-sleek` or model-matched directory), same interview discipline, riding with the plugin instead of a separate file installation. Its digest names `grill_user` as the only grilling transport and explicitly forbids `@grilling-sleek/cli`, and the content opens with the same transport discipline — field testing showed that without the explicit negation the model follows the CLI narrative this repository's own docs carry, shelling out instead of calling the tool.
2. **The durable record is the tool call itself.** A design review against the Harness source confirmed its persistence read path refuses session-event types outside the generated `KNOWN_SESSION_EVENT_TYPES` catalog — and only in-repo packages can enter that catalog. An out-of-repo plugin therefore cannot append a dedicated `grilling/*` event family; the v2 design's first-class in-repo route assumed a repository we do not own. Instead, the round's truth rides the records the Harness already writes for every tool call: the call arguments carry the full question batch, the tool result carries the answers, so replay, fork, and history see what was asked and answered. When the round raced on a Hub, the result also carries its linkage (`hub: { sessionId, url }`), tying the local roundId to the Hub session. An upstream contribution adding the event family remains a future option that would not change the tool's contract.
3. **Two answer links race at the tool-execute layer, not the event layer.** The downstream link is `userQuestions.ask()`; the Hub link is a client-side ≤60 s-window long-poll loop against the existing Hub REST API (same endpoints the CLI uses — `POST /v1/sessions`, `POST .../rounds`, `GET .../response?wait=`, `PATCH .../sessions/{id}`). A dedicated `AbortController` (chained from `exec.signal`) settles the loser: Hub wins → abort triggers the gateway's cancel frame everywhere else; downstream wins → the tool proxy-submits to the Hub, and on a 409-with-winning-response conflict a PUT revise converges the Hub to the recorded result. `NO_PROVIDER` from a headless profile is masked as "downstream absent", never an error; the race registers no `user-questions/request` listener and touches no one else's events. Before the card goes out, the Hub round opens first, bounded by a 2 s reveal budget, so the answer-page URL rides the card (the first question's `detail` — the one page every answerer sees; paged question UIs bury later detail, and the URL's reader is the user deciding where to answer, before they start) and is logged once per round, bare and trailing nothing; a form-level banner would be the more natural surface but needs a host UI extension (an `intent` variant), recorded with the upstream route. Past the budget the round still opens and races, only URL-less, and a fast permanent open failure degrades the round to downstream-only — warned, no `hub` in the result — rather than failing the call, while a round with no answerable link at all still fails explicitly.
4. **The main answer surface is the existing Hub CDN SPA** (`https://<cdn>/#session_id`), shared unchanged with the other agent tools — UX polish is a static redeploy that benefits every host at once. The SPA treats answers from elsewhere as first-class, because the race makes them routine (the tool's proxy submit, another tab): `response.created` arriving while a form still shows syncs the page to the session's current state, a fetched answered round never renders a form (its submit could only 409), and `round.created` switches along without a modal confirm — only the deliberate history view is never yanked, getting a non-modal notice instead. Web Push is deferred entirely (IM bridges already deliver platform-native push; the one uncovered cell — browser-only user with the page closed — degrades from instant to next-open).
5. **Signal wiring is a correctness requirement, not polish.** The tool registry never abandons the body promise, so every pending step of both links must observe the race controller; `roundTimeoutMs` (config, default 4 h) is the only orphan-round guard, enforced through the Harness cooperative timeout policy, and the abort path classifies a `TOOL_TIMEOUT` reason as expired and anything else as cancelled.

The package pins its `@deepseek-ai/dsh-*` peers against the published alpha channel, bundles with every peer external (bundling cordis would fork its module singleton), and ships its own vitest/eslint/tsc/prettier gates through `dsh/prek.toml`.

## Alternatives considered

**Land the package inside the Harness repository (the design's first-class route).** It would unlock the dedicated `grilling/*` event family and the repo's generated catalogs. It lost: that repository is upstream reference material we do not own, and its read-path gate refuses third-party event types outright — so the family is unreachable from here regardless of packaging. Recorded as the future-upstream path, not the delivery plan.

**Zero-code skill drop-in (keep the CLI under dsh).** Ship `skills/grilling-sleek/` into dsh's skill directories unchanged and keep the subprocess CLI as the transport. It lost: it inherits all six process-boundary mismatches above, and dsh's native seams (tools, user questions, session log) already delete the entire CLI layer. It survives only as the hubless degradation story when nothing better is installed.

**webserver-hosted answer page as the main surface (the original D3 shape).** Host a purpose-built answer page on dsh's `ctx.webServer` with capability tokens. It lost on the iteration lever: the Hub CDN SPA is already deployed, already serves the other tools, and redeploys for free — a dsh-only page buys a second surface to maintain and nothing the SPA lacks.

**`grill-relay` outbound WSS message relay (the D4 middle state).** An in-host plugin relaying grilling frames to the Hub over a persistent socket. Withdrawn after auditing the actual Hub: REST + clamped long-poll + SSE + idempotency + rate limiting already cover every requirement, so the relay added a connection to own for zero capability.

**Exclusive answerer in the waterfall (claim `user-questions/request` without calling `next()`).** Makes grilling the only answerer and the race unnecessary. It lost: it severs every ecosystem answerer (IM bridges, remote apps) from grilling questions — the exact composability this design buys.

**Listener-layer race (intercept `user-questions/request` and race the Hub against it).** v1's placement, withdrawn in v2: intercepting requires deciding "is this a grilling question" on someone else's event, which reaches plan-review and other askers' traffic. The execute-layer race achieves the same effect with zero event-footprint.

**Hub SPA as a dsh remote client (consume the `$events` wire protocol).** Would inherit cancel-frame convergence and first-answer-wins arbitration for free. It lost: it welds the SPA to dsh's protocol, forfeits the one-SPA-for-all-hosts neutrality and the Hub's host-agnostic position. Paying for convergence wiring inside the tool was judged the cheaper side of that trade.

## Consequences

What M1 shipped: the package under `dsh/` — the `grill_user` tool, the execute-layer race with dedicated-controller convergence, the Hub client (create session, open round, poll loop, proxy submit, revise, cancel), and the runtime skill registration — with no custom session events; `pnpm test`, `pnpm typecheck`, `pnpm lint`, and `pnpm build` pass in `dsh/`, the tool spec covering the race outcomes (downstream win with proxy submit and revise-on-conflict, Hub win with `NO_PROVIDER` masked, hubless+headless explicit failure, user abort, timeout expiry, session sharing across rounds), the answer-page URL riding the card and the result, downstream-only degradation on open failure, and the reveal budget elapsing without losing the race — all against a loopback stub Hub. `server/` has no behavioral change; its REST surface serves the dsh client unchanged (long-poll clamp, 409-with-winning-response, PATCH terminal idempotency). Distribution followed in [the distribution record](../proposed/2026-09-01-dsh-plugin-distribution.md): the npm bundle channel, an independent `0.0.x` version line, push-driven releases.

The costs accepted: the Harness is pre-release and its npm packages ride an alpha dist-tag (`0.1.2-alpha.x`); a seam rename lands as a same-batch dependency bump here. The dedicated `grilling/*` event family is unreachable from outside the Harness repo, so future structured UI cards must key off the generic tool records until an upstream contribution lands. The cancel frame carries no payload, so losing ends cannot show the winning answer and cannot distinguish "answered elsewhere" from "asker cancelled" — accepted as the race's UX cost, mitigated by the recorded result being authoritative and the Hub always converging to it. A late answer submitted in the milliseconds before cancellation arrives is accepted and silently dropped by the gateway; the window is race-narrow and the whole-round snapshot model means nothing half-applies. Hub authentication remains "possession of session_id"; the dsh process holds it after creating the session, which is exactly the authority the proxy submit needs but means a leaked id leaks the session — unchanged from the CLI era and covered by the same rate limiting. A degraded round answers without the Hub and is signalled only by a warning plus the absent `hub` field — a misconfigured `baseUrl` therefore converges nothing, and those two signals are its diagnosis surface. The surfaced URL is paste-sensitive (auto-linking swallows trailing punctuation), so the first question's detail and the log line end with the URL, and the tool's schema and the skill's content both instruct the model to echo it alone on its line. Finally, any missed `signal` branch in the two links would hang the agent loop after an interrupt; the race and its abort paths are the most heavily tested surface in the package precisely because this failure is silent. M2 (push/outbox on the Hub side) waits for a retention pain to justify it; M3 (an in-chat card and a hubless answer page) remains optional.
