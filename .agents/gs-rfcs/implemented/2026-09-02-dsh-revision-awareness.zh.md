# GS-RFC: dsh grilling 修订感知与会话生命周期

[English](2026-09-02-dsh-revision-awareness.md) | 中文

Status: implemented

## Problem

网页应答页允许用户在会话存活期间随时修订任意已答轮——按钮写着
"Update answers (notify AI)"，成功横幅写着 "the AI has been notified"——但
dsh 侧没有任何东西听得见修订。三处断裂，全部在接收侧：

1. `awaitResponse` 丢弃 202 pending 体——那是 Hub 已有的唯一带内信号
   （调用方停候期间，别的轮上落了修订时，`revised` 通知随 pending 响应
   一同返回）。
2. 工具调用一返回就再无监听者。调用之间的修订永远无人知晓——网页的
   承诺在 dsh 模式下是假的。
3. REST 面甚至无法表达"全部轮次答完后继续监听修订"：长轮询停在一个
   已答轮上会立刻返回 200，而 `revised` 通知只递给停在**未答**轮上的
   调用方。调用之间唯一携带修订的流是会话的 SSE。

对称地，插件开出的 Hub 会话没有任何东西去关闭：失败或中止的轮会取消
它，但正常结束的访谈让会话一直活到 1 小时 TTL——一个没有听众的修订
窗口。而且 race 的收敛注释宣称记录结果是"the truth"，而用户的修改只
存在于 Hub 侧：两个方向，一个真相归属问题。

## Decision

**Hub 是答案的唯一真相源；agent 持有的一切都是缓存。** 每轮的最新
revision——无论人类在哪个面表达，应答页或获胜卡片——就是决策。会话
日志是 append-only 历史，竞速的收敛语义不变（竞速赢家也是一次人类
表达，只是不同的面）。收敛分层叠加，任何一层失守都不丢修订
（`dsh/src/`）：

1. **修订 watcher**（`watch.ts`）——自第一个成功开出的 round 起，插件
   读取会话的 SSE 流（`GET /v1/sessions/{id}/events`，应答页用的同一条
   流）。每个 `response.revised` 取回该轮最新答案（`GET /rounds/{n}`）
   并按 jobs 模式带外送达 agent：空闲 agent 以 `followup` 唤醒，忙碌
   agent 在下一个步骤边界收到 `inject`。连续三次空闲唤醒为预算上限
   （一轮应答回填），超出的送达改为 inject 停放。每次（重）连接都用
   轮次摘要（`GET /rounds`）对比水位线重放——SSE 没有回放，漏掉的事件
   或断掉的流靠比对自愈。终态事件、被拒绝的流、agent 消亡或插件卸载
   都会停止 watcher。
2. **结果增量**（`race.ts` `syncRevisions`）——每个新 round 开出前，插件
   用 Hub 对齐每轮 revision 水位线，把新出现修订的轮次放进工具结果的
   可选 `revisions[]` 字段（轮号、分支名、revision、完整最新答案）。
   这也是 SSE 被屏蔽时的收敛路径。
3. **等待通知**（`hub.ts` `awaitResponse`）——长轮询循环收集 202 体携带
   的 `revised` 通知，这些轮的最新答案同样随结果送达。

水位线比对消解跨层重复：先送达的层推进水位线，其余层跳过。失败或
中止的轮取消 Hub 会话并重置链接（`closeHubLink`），下一次调用开全新
会话。

**不存在关闭动作，也不需要。** 会话活到 TTL（公共 Hub 上一小时），
这段生命周期*就是*用户的修订窗口——有意为之，不是疏漏。唯一的例外
是 agent 消亡（`index.ts`）：死掉的 agent 再也听不见修订，所以它的
watcher 停止、会话尽力取消——这是通道诚实性，让应答页显示
"cancelled" 而不是继续收集无人读的修订。连取消都丢失时，TTL 清扫器
是最终安全网。运行时 skill 正文（`skill.ts`）教给模型匹配的纪律：每轮
以最新 revision 为准，且模型没有也不需要任何关闭动作。

两条实现边界成立：零新增运行时依赖——Node 没有可靠的全局
`EventSource`（Node 24 上为 undefined，已验证），SSE 读取器是仓内自带
重连与退避的 fetch 流解析器，通知消息以类型导入 `dsh-llm` 后内联构造，
镜像该包的工厂。server 与 web 零改动——插件新用到的每个端点都已存在。

CLI 对齐（打包 skill 的修订纪律、`poll` 退出输出携带修订轮、
`complete` 回带合并终稿）刻意不在本次范围，留给独立记录。

## Alternatives considered

**纯拉取式收敛（结果增量、无 watcher）**被否决：调用之间的修订——
包括访谈结束后的每一次修订，最典型的"我改主意了"时刻——要等到一次
可能永远不会来的下一次调用才可见，网页 "the AI has been notified" 的
承诺只是延迟成谎而非成真。分层设计的代价是每个存活访谈会话一条 SSE
连接，对着 5 万连接的软限可忽略。

**`grill_done` 关闭工具**（模型调用的收束：终局全量同步后 `PATCH
complete`，返回合并终稿）被否决于方向："访谈达成共识"是工具无法精准
择时的语义判断，且用第二个工具承载它恰恰重新引入了 construction
rules 清单要吸收的条件 schema 问题。关闭自动化之后合并终稿也失去了
载体——见下一条。

**回合结束或空闲时机械自动关闭**被否决：回合边界不是访谈边界（多轮
访谈合法跨回合），且修订窗口比及时关闭更重要——用户明确称挂到 TTL
"无伤大雅"。*agent 消亡*时的自动 cancel 保留了下来：死掉的 agent 不是
暂停的访谈，而是没有听众的通道，应当诚实地关闭。

**内建或第三方 EventSource**被否决：Node 没有可靠的全局实现，为单一
解析器引入运行时依赖不值 ask-first 边界。仓内读取器（约 80 行）还拥有
现成客户端不提供的重连即重对齐纪律。

**只修 202 丢弃**被否决为不完整：它只覆盖轮次挂起期间落地的修订——
最不常见的窗口；调用之间的窗口才是修订真正死去的地方。

## Consequences

dsh 模式下修订零丢失：存活会话上的任何修订至少经三层之一到达模型，
水位线比对去重，会话终结后修订结构性不可能（Hub 以 410 拒绝）。应答
页的承诺成真，死通道诚实关闭，模型的总结纪律由数据支撑而非记忆
支撑。server 与 web 零改动，运行时依赖图保持一个包。

代价：每个存活访谈会话占用一条 SSE 连接直至其生命周期结束；唤醒预算
意味着连续超过三次的空闲期修订改为 inject 停放（下一个步骤边界送达
——延迟而非丢失）；屏蔽 SSE 的部署退化为下次调用送达；agent 未经干净
dispose 而死（进程崩溃）时其会话留给 TTL 清扫器；工具输出 schema 增加
可选 `revisions` 字段——增量式，但属于模型可见的契约变更。CLI 模式的
修订语义仍是本记录刻意留下的待办缺口。
